### 문제해결과정

1. **3D 시뮬레이션 중단**: 1차 회의에서는 3D 시뮬레이션으로 먼저 테스트하기로 했습니다. 디지털 트윈에서 앉은 사람 98.2%, 룸 판정 92.0%(112장)가 나왔지만 세 가지 이유로 뺐습니다. 엎드린 사람이 48.9%로 같은 모델이 실제 사진 6장을 모두 잡은 것과 정반대였고(점수가 모델이 아니라 그래픽의 한계를 재고 있었음), GPU 없이 렌더링하면 4명이 있는 룸을 0명으로 판정했으며, 가상 화면을 실제에 맞추는 시간이 실제 룸을 한 번 찍는 것보다 컸습니다. 하루 만에 멈추고 실제 룸 천장에 카메라를 달아 22분을 찍어 검증했습니다.
2. **테이블을 못 잡는 문제 → 파인튜닝**: 사전학습 모델은 책상을 식탁(dining table)으로만 배워, 천장에서 내려다본 우리 테이블을 거의 찾지 못했습니다(YOLO26s 2%). 16종을 같은 조건으로 비교했지만 테이블과 엎드린 사람을 둘 다 잡는 모델은 없어, 데이터 문제로 보고 우리 룸에서 만든 727장(학습 637 + 검증 90)으로 파인튜닝했습니다. 1차 학습은 테이블은 100%가 됐지만 사람을 잊었고(100%→68%), 사람 데이터를 같이 넣고 학습률을 낮춘 v2에서 둘 다 해결했습니다.
3. **생성형 데이터 실험**: 엎드린 사람 사진이 부족해, 빈 룸 사진의 의자 자리 4곳에 Stable Diffusion 인페인팅으로 엎드린 사람을 그려 넣고 CLIP으로 거른 뒤 눈으로 확인했습니다(합성 80장, 그중 엎드린 장면 40장). YOLO26s가 40장을 모두 잡아 새로 배울 것이 없었고, 진짜 약점이던 천장 각도의 테이블은 합성 사진으로 풀 수 없어 학습에는 쓰지 않았습니다. 대신 약점을 찾는 데 썼습니다. 후드를 쓰고 엎드린 사람은 YOLO26l도 신뢰도 0.14로 놓쳤고(26s는 0.42로 잡음), 의자에 외투만 걸린 사진은 어떤 모델도 사람으로 잡지 않았습니다.
4. **감지 영역**: 사각형 박스가 통로까지 덮어 지나가는 사람을 재석으로 세는 문제는 SAM으로 테이블 테두리만 따서 풀었습니다. 영역을 더 넓히면 유리벽 너머 옆방 사람까지 잡혀서, 영역은 +15%로 두고 겹침 기준을 25%에서 10%로 낮췄습니다.
5. **판정 위치**: 라즈베리파이 4B에서 같은 YOLO26s v2를 영상 659장으로 실측했습니다. 정확도는 같았지만 1장에 2,832ms(초당 0.35장, GPU 서버 18.1ms보다 약 156배 느림)가 걸렸고, 최고 81.3°C까지 올랐으며, 14대를 따로 관리해야 하고 초기 비용도 약 240만 원으로 PC 한 대보다 컸습니다. 그래서 GPU가 있는 교내 PC 1대에서 14개 룸을 모두 판정하기로 했습니다. 클라우드 GPU는 월 약 60만 원이 들고 영상이 학교 밖으로 나가 함께 제외했습니다.

| 모델 | 파라미터 | 테이블 | 엎드린 사람 | GPU 1장 |
|---|---|---|---|---|
| YOLO26n (전) | 2.6M | 3% | 65.5% | 17.9ms |
| YOLO26s (전) | 10.0M | 2% | 92.9% | 21.0ms |
| YOLO11s v2 | 9.5M | 100% | 98.8% | 17.7ms |
| **YOLO26s v2 (최종)** | **10.0M** | **100%** | **100%** | **18.1ms** |
| YOLO26m v2 | 21.9M | 100% | 100% | 21.6ms |

학습에 안 쓴 영상 기준입니다. GPU는 팀 노트북 RTX 5060, 입력 960, 30회 중앙값입니다.

### 1차 회의에서 정한 일과 결과

| 1차에서 정한 일 | 결과 |
|---|---|
| 모델과 임계값 합의 | 사전학습 16종 비교 후 YOLO26s v2로 결정, 엎드린 사람 기준값 0.35 |
| 실제 룸 고정 촬영 영상으로 판정 확인 | 천장 고정 카메라 영상 22분 촬영. 앞 80%는 학습, 뒤 20%는 시험에 사용 |
| 라즈베리파이 속도 측정, 추론 위치 결정 | 라즈베리파이 4B 실측 1장 2,832ms(초당 0.35장), 최고 81.3°C → 교내 PC 1대 서버로 결정 |
| 책상 검출 보완 | 파인튜닝으로 테이블 검출 2% → 100% |
| 기획서 반영, PPT 초안 | 발표 슬라이드 16장, 프로젝트 보고서 작성 |

그 밖에 한 일:
- 3D 디지털 트윈에서 엎드린 사람 검출이 48.9%로 실제(6/6)와 달라, 시뮬레이션 테스트를 중단하고 실제 영상 검증으로 바꿨습니다.
- Stable Diffusion으로 빈 룸 사진에 엎드린 사람을 그려 넣은 합성 사진 80장을 만들어 시험했습니다.
- 노트북 GPU 실측(1장 18.1ms)을 바탕으로 서버 최소 사양을 예측했습니다.
- 비용 계산표와 시스템 컨텍스트 다이어그램을 만들었습니다.
- MVP 사이트를 만들었습니다. 실제 룸 천장 카메라 영상 22분을 더미 데이터로 삼아 14개 룸을 가상으로 운영하는 관리자 대시보드 시뮬레이션으로, 저녁 식사 시간 룸 활성화율은 도입 전 22%에서 도입 후 50%로 나왔습니다.

### 조치 사항

- 판정은 교내 PC 1대에서 하기로 했습니다. 최소 GTX 1060급, 권장 GTX 1070급 + 라이젠 5 5600급(약 50만 원)입니다.
- 룸별 라즈베리파이와 클라우드 GPU(월 약 60만 원, 영상 교외 전송)는 제외했습니다.
- 감지 영역을 테이블 박스 30% 확대에서 SAM 테이블 테두리 +15%로 바꾸고, 사람 박스 겹침 기준을 25%에서 10%로 낮췄습니다.
- 합성 데이터는 학습에 쓰지 않고, 약점(후드 쓰고 엎드린 사람)을 찾는 데 활용하기로 했습니다.
- 비용을 룸 단위 구독(룸당 월 1.5만 원)으로 정하고, 점검·고장 수리(출장비 제외)·재학습 인건비를 포함했습니다.
- 발표 자료와 GitHub에 올린 사람 이미지는 모두 모자이크했습니다.

### 2. 테이블을 못 잡는 문제

- **고민**: 더 큰 모델이면 잡을까? 사전학습 16종을 같은 조건으로 비교했지만 테이블과 엎드린 사람을 둘 다 잡는 모델은 없었습니다. 크기가 아니라 데이터 문제라고 판단했습니다.
- **시도**: 우리 룸 사진 727장을 직접 만들어 파인튜닝했습니다. 테이블 라벨 181장은 전부 눈으로 검수했습니다.
- **실패**: 1차 학습은 테이블 위주 데이터라, 테이블은 100%가 됐지만 사람을 잊었습니다(사람 100%→68%, 가방 89%→14%).

### 3. 기존 YOLO 박스로는 감지 범위를 제대로 잡을 수 없는 문제
- **문제**: 감지 범위를 YOLO 테이블 박스를 30% 넓혀 만들었는데, 박스는 사각형이라 테이블 모양과 맞지 않았습니다. 비스듬한 테이블에서는 옆 통로까지 덮어 지나가는 사람도 재석으로 셌습니다.
- **고민**: 박스를 넓히거나 줄이는 것만으로는 통로와 테이블 끝자리를 동시에 맞출 수 없어, 기존 YOLO 인식 범위의 한계라고 판단했습니다.
- **시도**: 테이블 박스를 SAM에 넣어 테이블 테두리만 따고, 테두리를 15% 부풀려 감지 범위로 썼습니다. 사람에 가려지지 않은 빈 룸에서 한 번 따고, 테이블 위치가 달라진 상태가 30초 넘게 이어지고 사람이 없을 때만 다시 땁니다.
- **실패**: 테이블 끝에 앉은 사람을 잡으려고 범위를 더 넓히자 유리벽 너머 옆방 사람까지 잡혔습니다.
- **바꾼 것**: 범위는 +15%로 두고, 사람 박스의 겹침 기준을 25%에서 10%로 낮췄습니다.

| 15% | 96.9% | 1초 |
| **10% (최종)** | **97.5%** | **0초** |
| 1% | 99.5% | 0초 (통로에 선 사람까지 재석) |

천장 고정 카메라 영상에서 사람 555번(1초 단위 378초)을 기준별로 비교했습니다. 1%까지 낮추면 감지 범위에 살짝 닿기만 해도 재석이 되어, 짐만 남은 룸 앞 통로에 누가 서 있으면 부재 타이머가 계속 처음으로 돌아갑니다. 그래서 룸 판정이 틀린 순간이 없는 가장 높은 기준인 10%로 정했습니다.

| 빨강 · 사용 중 | 노랑 · 자리 비움 | 초록 · 이용 가능 |
|---|---|---|
| ![빨강](<2_비용·판정·발표준비/images/판정_빨강_사용중.jpg>) | ![노랑](<2_비용·판정·발표준비/images/판정_노랑_자리비움.jpg>) | ![초록](<2_비용·판정·발표준비/images/판정_초록_이용가능.jpg>) |

같은 룸에서 신호등 색이 바뀌는 모습입니다. 사람은 모자이크했습니다.

### 4. 비용이 너무 크게 나온 문제
- **문제**: 처음 계산한 초기 비용에는 PoE 스위치, 업체 시공, 현황판 모니터까지 들어 있어 학교가 내기엔 컸습니다.
- **시도**: 와이파이 홈캠(Tapo C210)으로 바꿔 PoE와 시공을 빼고, 현황판은 고도화로 미뤘습니다. 월 운영비는 룸당 1.5만 원 구독으로 정해 점검·수리·재학습 인건비를 넣었습니다.
- **결과**: 초기 207만 원, 연 252만 원으로 ERICA 학생지원비의 0.02%입니다.


![시스템 컨텍스트](<2_비용·판정·발표준비/images/시스템_컨텍스트_다이어그램.png>)

고객은 학교 운영 담당, 사용자는 학생입니다. 판정은 교내 PC 1대에서 합니다.

| 항목 | 계산 | 금액 |
|---|---|---|
| 카메라 (Tapo C210) | 14대 × 45,900원 | 64만 원 |
| 판정 서버 PC (DB 포함) | 1대 | 50만 원 |
| 문 앞 신호등 | 14개 × 35,000원 | 49만 원 |
| 전기 공사 | 전체 | 30만 원 |
| 카메라 고정 부자재 | 14곳 × 10,000원 | 14만 원 |
| PoE 스위치 · 1층 현황판 | 와이파이 카메라라 불필요 · 고도화 단계로 미룸 | 0원 |
| **합계** | **룸당 약 15만 원** | **207만 원** |

구독은 룸당 월 1.5만 원(연 252만 원)으로, 한양대 2026학년도 교비회계 자금예산서(ERICA)의 학생지원비 103.6억 원의 0.02%이고, 초기 비용을 더한 첫해도 0.04%입니다. Tapo C210은 앱 전용 홈캠과 달리 RTSP로 영상을 직접 받을 수 있어, 영상이 제조사 클라우드를 거치지 않습니다.

### 5. 서버 사양을 정할 근거가 없던 문제
- **문제**: 룸 14개를 1초에 1장씩 판정하려면 1장을 71ms 안에 처리해야 하는데, 학교 PC가 어느 사양이면 되는지 근거가 없었습니다.
- **시도**: 팀 노트북에서 YOLO26s v2(입력 960)를 30번 돌린 중앙값으로 재고, GPU 연산 성능(TFLOPS) 비율로 학교 PC급 GPU를 환산했습니다.
- **결과**: 최소 GTX 1060급, 권장 GTX 1070급으로 정했습니다. CPU는 카메라 14대의 영상을 받아 푸는 일을 맡으므로 6코어 라이젠 5 5600급, 램 16GB로 잡았습니다(PC 약 50만 원).

| 방식 | 1장 처리 | 초당 처리 | 71ms 기준 |
|---|---|---|---|
| CPU만 (라이젠 7 250) | 135ms | 7.4장 | 부족 |
| CPU + GPU (RTX 5060 노트북, 실측) | 18.1ms | 55장 | 3.9배 여유 |
| GTX 1070 (6.5 TFLOPS, 환산) | 약 42ms | 약 24장 | 통과 |
| GTX 1060 (4.4 TFLOPS, 환산) | 약 62ms | 약 16장 | 통과, 여유 적음 |

### 6. 말로는 전달하기 어려운 문제
- **문제**: 판정 방식과 도입 효과를 말로 설명하면 이해하기 어려웠습니다.
- **시도**: 눈으로 보는 것이 이해하기 쉽다고 판단해 MVP 사이트를 만들었습니다. 학습 데이터(실제 룸 천장 카메라 영상 22분)를 더미 데이터로 삼아 14개 룸을 가상으로 운영하는 관리자 대시보드 시뮬레이션입니다(룸 상태, 부재 기록, 통계·KPI, 도입 전/후 비교).
- **결과**: 저녁 식사 시간 룸 활성화율이 도입 전 22%에서 도입 후 50%로 바뀌는 것을 한 화면에서 보여 줄 수 있게 됐습니다.


![MVP 관제 대시보드](<2_비용·판정·발표준비/images/대시보드_도입전_1830.png>)

도입 전 18:30 화면입니다. 14개 룸 중 사용 중 2개, 30분 넘게 짐만 있는 룸 8개, 룸 활성화율 14%입니다. 도입 후에는 저녁 식사 시간 활성화율이 22%에서 50%로 올라갑니다.

| 지표 | 도입 전 (아무도 안 치움) | 도입 후 (초록불 → 짐 치우고 사용) |
|---|---|---|
| 룸 활성화율 | 22% | 50% |
| 30분 넘게 짐만 있는 룸 평균 | 6.4개 | 0.6개 |
| 초록불이 켜진 뒤 다시 사용까지 평균 | 47분 | 2분 |

같은 날 시나리오로 비교한 시뮬레이션이라 실제 운영 수치는 아닙니다. 실제 효과는 시범 운영에서 확인해야 합니다.

## 결론

2주차에 한 일은 다섯 가지로 정리됩니다.

- **데이터로 푼 테이블 문제**: 모델 크기가 아니라 데이터 문제임을 16종 비교로 확인하고, 727장 파인튜닝으로 테이블 2%→100%, 엎드린 사람 92.9%→100%를 얻었습니다. 1차 학습에서 사람을 잊은 문제도 데이터 구성과 학습률로 풀었습니다.
- **모양대로 잡는 감지 범위**: SAM 테두리 +15%와 겹침 기준 10%로 통로·옆방 오탐을 막으면서, 사람이 있는데 룸을 비었다고 보는 순간을 없앴습니다.
- **학교가 낼 수 있는 비용**: 초기 207만 원, 연 252만 원(학생지원비의 0.02%)으로 정리했습니다.
- **실측으로 정한 서버 사양**: 노트북 실측(1장 18.1ms)을 환산해 최소 GTX 1060급, 권장 GTX 1070급으로 정했습니다.
- **눈으로 보여 주는 결과**: MVP 관제 대시보드로 도입 효과(저녁 식사 시간 활성화율 22%→50%)를 한 화면에서 보여 줬습니다.
